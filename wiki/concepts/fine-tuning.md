## Overview

Fine-tuning is the process of continuing to train a pretrained language model on domain-specific data to specialize its behavior, knowledge, or output format. It bakes information into the model's weights, in contrast to [[concepts/rag-vs-index-based-retrieval]] which injects knowledge at inference time via context windows.

Fine-tuning sits on a spectrum of approaches for putting knowledge into models, from lightweight prompt engineering to full parameter updates:

**Prompt Engineering → RAG → [[concepts/parameter-efficient-fine-tuning]] → Full Fine-Tuning → [[concepts/domain-adaptive-pretraining]] → Pretraining from Scratch**

Each step rightward increases cost, data requirements, and depth of knowledge integration, but also increases the model's fundamental capability in the target domain.

## When to Fine-Tune

Fine-tuning is appropriate when:
- **Domain-specific behavior** is needed (terminology, tone, reasoning patterns)
- **Latency matters** — no retrieval step needed at inference
- **Privacy/offline** requirements preclude API calls
- **Consistent formatting** — structured outputs like JSON, SQL, or domain-specific schemas
- **Cost optimization** — smaller fine-tuned model replaces expensive large model API

Fine-tuning is NOT ideal when:
- Knowledge changes frequently (use RAG instead)
- You need traceable citations to source documents
- Training data is very limited or noisy
- The base model already handles the task well with prompting

## Methods

### Full Fine-Tuning
Updates all model parameters. Highest quality but requires massive compute (60GB+ VRAM for 7B model) and risks [[concepts/catastrophic-forgetting]]. Rarely practical for most organizations.

### Parameter-Efficient Fine-Tuning (PEFT)
Updates only a small subset of parameters. See [[concepts/parameter-efficient-fine-tuning]] for details on [[concepts/parameter-efficient-fine-tuning|LoRA]] (0.5-5% of params, 90-95% quality) and QLoRA (4-bit quantized base, 80-90% quality).

### Instruction Tuning
Fine-tuning on instruction-response pairs to improve instruction following. Often uses [[concepts/synthetic-data-generation|synthetic instruction data]].

### RLHF / DPO
Aligning model outputs with human preferences. Uses reward models or direct preference optimization.

### [[concepts/raft|RAFT]] (Retrieval Augmented Fine-Tuning)
Hybrid approach: fine-tune the model on questions with both relevant and distractor retrieved documents, teaching it to leverage retrieval while ignoring noise. Achieves up to 76% improvement over baselines.

## The Training Data Question

Fine-tuning quality is dominated by data quality, not model size or training compute. As demonstrated by [[entities/microsoft-phi]]:
- Phi-1 (1.3B params) trained on "textbook quality" data rivals 10x larger models
- Phi-4 surpasses its teacher (GPT-4) on STEM benchmarks through synthetic data quality

Sources of fine-tuning data:
1. **Human-annotated**: Highest quality but expensive and slow
2. **[[concepts/synthetic-data-generation|Synthetic]]**: Scalable and cheap; requires rigorous quality filtering
3. **[[concepts/knowledge-distillation|Distilled]]**: Generated by a stronger teacher model
4. **Domain documents**: Converted to instruction format via automated pipelines

## The Three-Layer Architecture

For domain-specific LLM deployment, the emerging best practice combines three layers:

1. **[[concepts/domain-adaptive-pretraining]]**: Continued pretraining on unlabeled domain text (broad domain knowledge)
2. **Task-specific fine-tuning**: Supervised learning on labeled examples (specific skills)
3. **RAG at inference**: Real-time retrieval for current, traceable facts

This corresponds to putting knowledge into three places:
- **Model weights** (pretraining + fine-tuning): Persistent knowledge, fast inference
- **Context window** (RAG): Dynamic knowledge, traceable citations
- **External tools** (function calling): Real-time computation and data access

## Practical Considerations

- **Hyperparameters**: Learning rate, batch size, and epochs require careful tuning; too much training → overfitting and [[concepts/catastrophic-forgetting]]
- **Evaluation**: Mix of quantitative metrics and human review; domain experts must validate outputs
- **Compute**: LoRA on consumer GPUs; QLoRA on free Colab; full fine-tuning needs A100s
- **Iteration speed**: Start with prompting, add RAG, then fine-tune only when needed

## RAG + Fine-Tuning: Complementary, Not Competing

The [[sources/rag-vs-finetuning-agriculture|agriculture case study]] provides empirical evidence that RAG and fine-tuning yield cumulative benefits: fine-tuning alone improved accuracy by 6+ percentage points, RAG added another 5 points, and the combination improved geographic knowledge transfer from 47% to 72%. The best 2026 pattern: **put volatile knowledge in retrieval, put stable behavior in fine-tuning**. See [[comparisons/rag-vs-fine-tuning]] for a full comparison.
